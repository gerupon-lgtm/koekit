# 要件定義書：ピタリズム

音声で位置を指定してカードをめくる未就学児向け知育Webアプリ。コエキットにおける音声認識検証の1本目。

### B：変更してよいが記録する

指示に従い、該当行の更新と改訂履歴1行の追記を行う。発案者の明示指示があれば、重ねて承認を求めない。

- **C-3: 2段階確定（認識結果を図示してから確定語で実行）を省略しない。** 誤認識がそのまま結果になる実装にしない
- **C-4: コロガリズム（既存公開作品）のコードを変更しない**

## 2. 背景・目的

### 2.1 背景

発案者はスマートフォンのWebアプリ（PWA）を個人開発しており、端末の傾きで球を転がす迷路ゲーム「コロガリズム」を公開済みである。傾きセンサー、物理挙動、迷路生成、オフライン配信までの実装実績がある。

その延長として、**音声を操作手段として使えるか**を確かめたい。大規模言語モデル（LLM）は使わず、「右上」「決定」「ストップ」といった限られた操作語だけを認識する軽い仕組みを前提とする。

音声認識の実用性を検証するのは今回が初めてであり、これまでは資料上の数値（Voskのモデルサイズ約48MBなど）で判断してきた。**実測値がないことが着手できない理由だった。**

### 2.2 目的

1. **Androidの実機で、音声認識が操作手段として実用に足るかを数値で確かめる**（精度・遅延・安定性）
2. **未就学児が位置を表す言葉（左右・上下・中央・斜め）を覚える遊びとして成立させる**
3. 検証で得た音声入力の部品を、コエキットの後続試作へ引き継げる形にする

### 2.3 作らなかった場合に起きること

**何も起きない。** 納期・外圧・依頼元はない。この事実は要件の性格を決めるため明記する。**合格ラインを実測後に動かせるB区分としているのは、これが根拠である。**

## 5. 利用シナリオ

### 5.1 初回価値（マイク許可から最初の成功体験まで）

公開前提であるため、初見の利用者が最短で価値に到達する経路を要件とする。

1. タイトル画面を開く
2. 保護者が「はじめる」をタップ → **マイク許可を求める**（【想定】このタイミング）
3. レベル0（練習）が始まる
4. 「スタート」と言う → 数字が回り始める
5. 「ストップ」と言う → 惰性で滑って止まる

**到達条件** — ここまでで「声で操作できた」という体験が成立する。**マイク許可から2操作で到達する。**

### 5.2 本編の1試行（レベル1〜5）

1. 「スタート」→ フォーカスがカードの上を移動し、徐々に速くなる
2. 「ストップ」→ フォーカスが止まる（惰性で少し滑る）
3. 止まった位置を言う（例：「みぎ」）→ **認識結果が矢印で表示される**
4. 矢印が合っていれば「決定」→ カードがめくれる
5. 動物の絵が表示され、鳴き声が鳴る

**矢印が違っていたら言い直す。** 言い直しは失敗ではない（8.4参照）。

### 5.3 行き止まりと復旧

| 状況 | 挙動 |
|---|---|
| マイクを許可しなかった | **タッチで全操作を続行できる。** その状態を子どもにも分かる画面表示で示す（C-2） |
| マイク許可を後から与えたい | **【想定】** タイトル画面から再度許可を求められる |
| 認識されない | 何も起きない。カウントもされない。言い直せる |
| 子どもが黙ってしまった | **【想定】** 受け付け区間のまま待機する。タイムアウトは設けない |
| 認識セッションが落ちた | 自動で再開する。復帰できれば正常動作とする（11.1） |
| 音声認識が使えない端末・ブラウザ | タッチのみで遊べる。ログは取れない |
| ゲームオーバー | 認定書を表示 → タイトルに戻る。同レベルの続きからは再開しない |

### 8.3 受け付け区間と語彙（F-002）

レベル紹介は `await_intro`（オーケー／オッケー、既存の確定語も可）、認定書は `await_next`（つぎ／次）を受け付ける。紹介を閉じる操作とゲーム開始の「スタート」は分ける。効果音中は停止し、認定書表示の750ms後から再開する。タッチで先に進んでも音が終わるまで待つ。ゲームオーバー・延長クリア後の「つぎ」は従来のボタンと同じくタイトルへ戻る。

**常時認識は行わない。** 区間ごとに認識を開始・停止し、その区間で必要な語だけを受け付ける。**区間ごとに語彙を絞ることで誤認識そのものが減る**（位置語待ちで「スタート」を受け付けないなど）。

| 区間 | 受け付ける語 | 画面 |
|---|---|---|
| レベル紹介 | オーケー／オッケー（既存の確定語） | 紹介と大きなチェックボタン |
| 認定書の次へ待ち | つぎ／次 | 大きな次へボタンと受付マイク |
| スタート待ち | スタート | 受け付け中を表示 |
| ストップ待ち | ストップ | 受け付け中を表示。フォーカス移動中 |
| 位置語待ち | そのレベルの位置語のみ | 受け付け中を表示。フォーカス停止 |
| 確定待ち | 確定語（決定・オーケー・オッケー）、位置語（言い直し用） | 矢印または中点を表示 |
| 結果表示中 | **なし（認識停止）** | 動物と鳴き声 |

**鳴き声と認識の干渉は、この区間設計により発生しない。** 鳴き声が鳴るのは結果表示中で、認識が停止しているため。

**確定待ち区間で位置語を受け付けることの副作用について** — 周囲の音を位置語として拾い、矢印がすり替わる可能性がある。**対策は入れない**（区分B、8.6参照）。

### 8.4 成否の判定（F-012）

| 区分 | 定義 |
|---|---|
| **正解** | 動物が表示された（止まった位置のカードをめくれた） |
| **失敗** | 動物が表示されなかった（止まった位置と違うカードをめくった） |
| **カウント対象外** | 認識されなかった場合。何も起きないため試行が成立しない |
| **失敗ではない** | 矢印を見て言い直す行為。確定語の発話前は承認が成立していない |

**判定の根拠** — 確定語の発話はプレイヤーによる承認である。**矢印を見て承認した結果は本人が受け入れたものとして扱う。** したがって「認識器が間違えたせいで失敗した」という状態は原理的に発生しない。この構造がC-3（2段階確定）の存在理由でもある。

**レベル遷移条件** — 同一レベルの試行は最大5回。**3回正解でクリア**（4回目・5回目を待たずに次へ進んでよい）。5回で3回に届かなければ**ゲームオーバー**。

**ゲームオーバー後** — 認定書を表示し、タイトルに戻る。同レベルの続きからは再開しない。

**設計意図（後工程で緩めないこと）** — 無制限にやり直せる設計は向上心の妨げになるという発案者の判断により、ゲームオーバーを設ける。**「やり直せたほうが親切では」という善意の緩和を行わない。** 変更する場合は区分B（記録が必要）。

**文字を使わない。** 未就学児が主利用者であり、文字が読めないことを前提とする。

**認識結果の図示（F-009）**

| 位置 | 表示 |
|---|---|
| 上・下・左・右 | その向きの矢印 |
| 左上・右上・左下・右下 | 斜め向きの矢印 |
| 中央 | **中点**（矢印では方向を表せないため） |

矢印・中点の大きさ・色・動きは**区分A**（実装時に決めてよい）。

**受け付け状態の表示（F-003）** — 受け付け中かどうかを文字以外で示す。**【想定】** マイクの絵の色、枠の発光など。表現は区分A。

**マイク未許可の表示** — タッチで遊べる状態であることを、子どもにも分かる画面表示で示す。

**認定書（F-015）** — 到達レベルに応じた名称を与える。**名称候補【想定】**：ひだりみぎマスター（Lv1）／うえしたマスター（Lv2）／なかまマスター（Lv3）／ななめマスター（Lv4）／ぜんほうこうマスター（Lv5）／スピードマスター（延長）。**名称・デザイン・レベル対応・プレイヤー名の入力有無はすべて区分A**（実装時に決定してよい。文書更新は任意）。

**フォント** — M PLUS Rounded 1c。**アイコン・ヘッダ構成はSIKUMI LAB他作品と揃える方針だが、具体は後決定**（R-06）。

### 8.6 レベル構成（F-013）

| レベル | 配置 | 枚数 | 新しく使う語 |
|---|---|---|---|
| 0 | ルーレット（練習） | — | スタート・ストップ |
| 1 | 左右 | 2 | 左・右 |
| 2 | 上下 | 2 | 上・下 |
| 3 | 上下左右＋中心 | 5 | 中央 |
| 4 | 四隅 | 4 | 左上・右上・左下・右下 |
| 5 | 3×3 | 9 | （なし。既出9語の総合） |
| 延長 | 3×3・高速 | 9 | （同上） |

**レベル4（四隅）を設けた理由** — 斜め4語は他の位置語より長く、認識が落ちやすい。レベル3から直接9枚へ進むと「9枚になったから難しい」のか「斜め語が認識されない」のかが混ざるため、斜め語だけを切り出して測れる段を挟む。

**延長ステージ（F-014）** — レベル5クリア後、**自動的に突入する。以降はタイトルから直接挑戦できる。** 速度を上げ、規定回数クリアで「スピードマスター」。最終レベルで5回失敗にならない子への対応であり、実質のエンディングとなる。規定回数は**区分B**。

### 8.7 操作語の一覧

| 分類 | 語 | 備考 |
|---|---|---|
| 抽選・停止 | スタート、ストップ | 「停止」も同義で受ける**【想定】** |
| 位置（上下左右） | 上、下、左、右 | |
| 位置（中央） | 中央、真ん中 | 「中」まで受けるかは精度を見て判断（区分B） |
| 位置（斜め） | 左上、右上、左下、右下 | |
| 確定 | 決定、オーケー、オッケー | **「決定」は硬く子どもには言いにくいため同義語を用意する。どちらが拾いやすいかも検証対象** |

**表記揺れは登録した語との照合で吸収する。** 「上」を含む発話なら何でも上と解釈するのではなく、登録語と照合する。登録外の発話・雑音は「何もしない」として扱う。**認識文字列をログに残すのは、この照合リストを後から補強するためである**（9.1）。

### 8.8 動物の絵と鳴き声（F-011）

- **モチーフ** — 身近な実在のペットをデフォルメした画像。発案者が用意する
- **種類数** — **区分A**（実装時に決定）。1試行でめくるのは1枚のみで残りは裏のままなので、**盤面の枚数と種類数は連動しない**。「同じ動物ばかりだと飽きる」という観点だけで決まる
- **鳴き声** — めくった動物の鳴き声を鳴らす。結果表示中は認識が停止しているため干渉しない
- **権利** — 発案者が用意する素材のため、外部素材の権利確認は不要

|---|---|

## 10. 音声認識方式の要件

### 10.1 方式の候補と位置づけ

| 方式 | 内容 | 位置づけ |
|---|---|---|
| **A. Web Speech API（既定）** | ブラウザ標準。端末内処理か外部処理かはブラウザの裁量。Android Chromeは従来サーバー側処理 | **検証専用。**発案者本人の声で基準値を取るためのみに使用。**公開版には使用しない（C-1）** |
| **B. Web Speech API（端末内処理）** | 同APIで `processLocally: true` を指定し端末内処理を必須にする。音声は外に出ない。モデルはブラウザ側が保持し自前配布が不要 | **有望な代替。**通ればCより有利。**日本語（ja-JP）とAndroidでの可否が未確認で、フェーズ0で最初に測る** |
| **C. Vosk（WebAssembly）** | 日本語モデルをブラウザ内で実行。音声は外に出ない。モデル約48MB（未実測）を自前配布。語彙を絞った指定が可能 | **本命。**公開版の既定候補 |

**公開版は B または C のいずれかとする（C-1）。**

### 10.2 不採用とした方式

| 方式 | 不採用の理由 |
|---|---|
| **D. 自前の小型単語モデル** | 閉じた分類器は入力を必ずどれかの語に割り当てるため、「その他」（雑音・BGM・無関係な会話）を無反応にする学習データが操作語本体より量を要する。加えて大人の声で学習したモデルは**子どもの声で最も崩れる**。主利用者が未就学児である本件と相性が悪い |

### 10.3 実装上の要件

- **入力層を差し替え可能な形に分離する。** 方式A・B・Cを同じインターフェースで扱い、ゲーム側のコードを変えずに切り替えられること。**コエキットの後続試作へ引き継ぐ共通部品となる**
- **認識セッションが途中で終了した場合、自動で再開する。** Android Chromeでは連続認識が途中で終わる挙動が知られている
- **区間ごとの認識開始・停止を繰り返すため、停止処理を毎回踏むことになる。** 安定性はフェーズ0の実機検証で確認する（11.1の連続使用指標）

### 10.4 BもCも合格ラインに届かなかった場合

**判断は都度行う。見送り条件を事前に要件化しない。**（外圧がなく、事前に決める必要がないため）
