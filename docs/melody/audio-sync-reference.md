## 新作で追加検証が必要なこと

- 元資料は主に8小節、新作は最大129小節。60 BPMなら約8分36秒（拍上の時間）である。開始アンカーだけで最後まで十分か確認し、必要なら小節境界等で音声基準へ表示を合わせ直す方式を比較する。
- Web Animationsの表示時計とAudioContextの時計は同一そのものではない。資料のv35でも表示側の微小差が残るとされている。滑らかさと同期精度を別々に測定する。
- AudioContext内の時刻と実際に耳へ届く時刻の差、マイク入力・解析処理の遅れは別の問題。タップ用の保存補正値をハナウタ検出へそのまま流用しない。16分への丸め前の時刻基準を検証する。
- 停止・送りで再生位置と表示位置を同時に更新。予約済みの旧音を止め、途中の持続音をどう再開するかを定義する。
- タブ非表示・画面ロック・AudioContextのsuspend/resume時に、壁時計だけで曲終了や次パターンへ進めない。復帰方針は基本設計で定義する。
- グリッド・五線譜・シーケンスの各表示を同一データで比較し、長音・休符・小節またぎ・エンディング1小節の境界も確認する。
- 診断は音声／壁時計の差、フレーム間隔、描画時間、予約周期、AudioContext状態をメモリ内で集計し、演奏後に表示する方式を参考にする。診断DOM更新が演奏へ負荷を加えないようにする。
- Android/iOS/PC、音量あり／なし、低モーション、60/120/180 BPM、4小節／最大長を検証する。ハナウタ時のカウント音・ガイドのマイク回り込みは別試験。

## 2026-09-27：ML-T01-v7のクリック／検出時刻の照合

発案者から、BPM連動だけでなく予約したクリックと音検出の時刻差を確認するよう指摘。元資料3節・11節・v34〜36と現行`probe/saezuri/{capture,capture-support,worklet,worker,analyzer,audio}.js`を読み直した。

- 録音中のクリックは`AudioBufferSourceNode.start(time)`で全拍を先に予約。25msの先読みschedulerは試聴側の処理であり、録音クリックをそのタイマーで鳴らしてはいない。ログの`playback.maxTimerGapMs`も録音クリックの遅延実測には使えない。
- 録音Workletも同じAudioContextのフレーム番号を使用。クリックの曲頭`musicalStart`に推定入出力遅延と手動補正を加えた時刻から録音し、解析の時刻0とする。したがってアプリ内の別時計がそのまま原因という証拠はなく、補正後に実際の音響経路が合うかが未検証。
- Pixel v7では`musicalStart=68.6406667s`、`startFrame/48000=68.6833333s`で、差は約42.7ms。Windows v7では差63ms。これはコードが適用した補正であり、クリックをマイクで測定した往復遅延ではない。
- `countTimes`は予約時刻。実際にスピーカーから出た時刻／耳へ届いた時刻やマイクへ届いた時刻は記録していない。Workerの解析完了時間も発声位置には使用していない。推定値の過不足と検出境界の偏りは別に調べる。
- シェーカーは包絡線が0から始まり、小節頭40ms・通常20ms。予約開始時刻と知覚されるアタックは厳密には同じとは限らない。包絡線の差だけを16分遅れの原因とは断定しない。
- 入力ノード接続後に350ms先のアンカーを決定しているが、最初のシェーカーバッファ生成はその後。録音側には予約時点の残り猶予や遅れの診断がなく、入力ストリームが実際に動き出したことを確認する準備完了通知もない。元資料v36の開始猶予消費と、OS処理ON時のカウント欠落に関連する可能性はあるが未実測。

次の検証は、同じ音声時計で予約時刻・録音フレーム・丸め前の検出境界を比較し、実機の入出力経路を通した校正と区別する。複数BPMで偏りが一定msか拍に比例するかを比較する。ユーザーの歌唱だけから端末遅延を分離したと扱わず、旧PoCのタップ補正値は流用しない。この追記は調査記録で、実装／公開版は変更していない。

### 提案：ドンカマを同時収録して拍の位置を測る

発案者の案「ドンカマも一緒に録って後で除去してタイミングを見る」。スピーカーからマイクへ入ったクリックを同じ録音の声と比較する方式として有効な検証候補。再生元のデジタル波形を単に録音へ混ぜるだけでは実際の入出力経路を測れない。

現行は歌唱区間だけを保持し、Workerで高域シェーカーを低域通過フィルターにより抑えてから声を解析している。案ではカウントインから端末メモリ上で捕捉し、フィルター前の信号から既知のシェーカーとの相関・高域の包絡線等でクリック位置を検出する。複数クリックの予約との差とばらつきを計測し、声は別経路で既存のフィルターを通して解析。丸め前の声の境界を、録音内の実測クリックが示す拍へ対応づける。推定入出力遅延へ実測往復遅延をそのまま加算して二重補正しない。

既知波形の探索には相互相関によるmatched filterが参考になる（[SciPy公式の相関・雑音中の波形検出例](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.correlate.html)）。これは手法の参照であり、Python/SciPyの導入決定ではない。スピーカー／部屋による波形変形と反射があるため、元波形の単純減算で完全除去できるとは扱わない。目的はまずクリック位置の計測と音符化の抑制で、加工済み音声ファイルの生成ではない。

イヤホンやOSのエコー抑制でクリックが捕捉されない場合、校正不可として既存補正へ戻す。クリックのマイク到達は耳への到達そのものではなく、声の音程判定の境界ずれも別に残る。音声は端末内処理・保存／送信なしを維持し、診断は検出した時刻と信頼度等に限定する。未実装の検証案として記録。
