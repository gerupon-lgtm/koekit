# ハナウタ試作v4 — 長音の揺れによる分割を抑える

2026-09-27。発案者の「音程・デュレーションの両方。特に長音のつもりなのに分かれる」という追加回答を受けた調整。v2の音符ログは音高フレームや波形を含まないため、実際にビブラートしていたか、7音のどこが誤検出だったかは断定できない。

## 変更

- 取り込みの初期設定を「音の区切り：長音を保つ（ハナウタ）」にした。分割の判断には前後125msずつ（計250ms）の平均音高を使い、近接する音高への変化は標準で180ms（ならし120msでは240ms）持続するまで分割しない。短い往復の揺れを一音として平均し、最も近い半音へ丸める。発声直後の基準も最初の一フレームから短区間の平均へ変更。無音や不明区間を越えて平均しない。
- 確定した音高変化の開始は、確認が済んだ時刻ではなく変化の開始まで戻す。短時間・250msの両方の平均で1.5半音以上変わる場合は短時間の値と短い確認時間を使い、長い平均窓が跳躍の途中に作る見かけ上の中間音を採用しない。
- 速い半音フレーズ向けに「細かい変化も拾う（従来）」を残す。長音設定は細かい近接音をまとめる場合がある。「ならし：なし」は双方の抑制をOFFにする比較条件。設定は次回の取り込みに適用し、既存候補を自動で変更しない。
- 16分クオンタイズでは開始・終了をそれぞれ丸め、長さが0になる極短区間は採用しない。従来の「全断片を最低1tickに伸ばし、次の音を押し出す」処理を廃止。音符が残らない場合は空の取り込みとして再試行を案内する。
- 無音は休符として維持。不明区間の補完条件（短時間・両側同音・片側不可）は変更しない。遅延推定と手動補正、明示的な頭合わせ、v3のカウントを維持。
- 診断のprototypeは`ML-T01-v4`、`captureOptions.noteMode`は`sustain`または`detail`。

譜面は引き続き長音を拍ごとのタイで表示する。これは音符データの分割とは別で、一つの長音は再生時に途中で再発音しない。カウントに食い込むシンコペーションは[v2の未決メモ](humming-v2.md)に残す。

## 実機追記：Pixel 6a（2026-09-27受領）

発案者の所感：「やはり頭が休符になってしまう。でも、かなり近づいた」。Windowsの追加データを続けて共有予定。

- 記録時刻：`2026-09-26T23:55:30.559Z`、ML-T01-v4、120 BPM、48kHz、4096標本窓、長音設定、ならし80ms、OS処理OFF、録音／試聴カウントON。
- 今回の発音区間方式は **`window-start`（旧方式）**。既定の`energy-gated`と異なる条件として比較する。この違いだけで先頭休符の原因とは断定しない。
- 8音、先頭tick1、頭合わせ0、追加補正0ms、自動補正約43.7ms。120 BPMの1tickは125msなので、出力譜面に16分休符が残っている。量子化後の位置であり、機器遅延が正確に125ms残ることを示す値ではない。
- 音符（startTick / durationTick / MIDI）：`1/2/55, 3/4/54, 9/1/51, 11/2/52, 15/9/54, 25/1/49, 27/2/51, 31/30/47`。冒頭55→54の分割も残る。最後の47は30tickの長音で、不明区間約42.7msを補完。
- 375フレーム中306検出・29不明、unknownSeconds約0.619、解析2628ms。ratio約0.913は周期検出比率であり音程正答率ではない。

提供ログには各フレームの時刻・種類・丸め前音高や波形が含まれず、冒頭が無音だったか周期不明だったかは判別できない。発声の立ち上がり、検出境界、入出力遅延推定の残差をこのデータだけで切り分けず、Windowsの条件と併せて検討する。意図した弱起を一律に詰める変更は行わない。

## 実機追記：Windows 11の方式比較（2026-09-27受領）

発案者の所感：「現時点での感触ですが旧方式の方が期待に近そう」。添付は`window-start`、本文は`energy-gated`。両方とも`noteMode: sustain`なので、ここでの旧方式は発音区間の方式を指し、音の区切りの`detail`とは区別する。次の調整の比較基準に旧方式での感触を残す。既定値・公開コードはこの記録追加では変更しない。

共通条件：ML-T01-v4、120 BPM、48kHz、4096標本窓、ならし80ms、長音設定、RMS下限0.008、不明区間上限150ms、OS処理OFF、カウントON、自動補正62ms、追加補正0ms、頭合わせ0。

Windowsでは両方式で先頭休符がなく、冒頭の54は一音に保たれた。主な違いは2音目の開始（旧方式が1tick早い）・長さ（旧方式が1tick長い）・音高（旧51、新50）、最初と最後の長さ。旧方式は最初と最後に短い不明区間の補完あり、新方式は全音detected。新方式の周期検出比率が高くても、発案者の意図に近いことを意味しない。

別々に歌った2回の記録なので、差をすべて方式の効果とは断定しない。Pixelの旧方式は8音・先頭tick1・冒頭55→54、Windowsの旧方式は7音・先頭tick0・冒頭54一音。この結果から旧方式が先頭休符の原因とは言えず、端末・発声の立ち上がり・未検出と遅延推定の残差を切り分ける課題として残す。音数7の一致だけで音程・タイミングの実機受入完了とはしない。
