# ハナウタ試作v8 — ドンカマの同時収録によるタイミング計測

2026-09-27。発案者の「ドンカマも一緒に録って後で除去しタイミングを見る」「是非やってみたい」に対応。共有された同期資料の照合を踏まえた試作。公開先は[試作ページ](https://koekit.sikumilab.com/probe/saezuri/)、公開確認は[公開記録](preview-deployment.md)。

## 目的と変更範囲

v7のPixelは前のめりに歌って期待する再生になった結果であり、自然な歌唱の時刻精度が解決したとは扱わない。v8はスピーカーからマイクへ実際に入った準備カウントで入出力経路の時間差を計測する。音程・長音判定・16分量子化は維持し、BPMに比例した一律前倒しは追加しない。譜面の音価表示・編集、OS音声処理ON時のカウント欠落は別の残課題。

## 操作

「録ったドンカマでタイミングを合わせる（試作）」を既定ONで追加。まずスピーカー、カウント音ON、OS音声処理OFF、追加補正0で自然に拍へ合わせて歌う。準備カウント中は声を出さず、カウント後に4小節歌う。終了後の表示で「ドンカマ実測：…ms」「従来の推定補正」のどちらを使ったか確認し、記録をコピーする。チェックを外せば従来条件との比較ができる。

イヤホンなどでクリックがマイクへ入らない場合は実測不可。Bluetoothの遅延を自動解消できると保証しない。計測範囲は0〜750ms、先頭アクセントの検出が必須。高域を強く落とすマイク・音声処理や反響でも検出できない場合がある。端末別の実測補正を永続保存する機能はまだなく、毎回のカウントで測る。追加ms補正は既存の端末内保存を維持。

## 処理

- `acoustic-sync.js`はDOM非依存の計測・録音区間選択。再生する既知のシェーカーと、録音信号の同じ高域強調処理後の正規化相関を取る。粗探索後に全標本で検証し、相関0.35以上かつ高域RMS0.0003以上を候補とする。閾値は試作値。
- 6発の準備音（beat 0,2,4,5,6,7）を照合。最初のアクセントで0〜750msを探索し、残りはその差±45ms以内。中央値から±12ms以内の4発以上、採用した差の最大最小差12ms以下で成功。雑音や欠落・不安定な結果は推定へ戻す。演奏中の追従補正／クロックドリフト推定は未実装。
- 音源バッファを準備してから350ms先の開始時刻を確定。カウントの100ms前から、曲末の最大1.2秒後までWorkletで端末内収録する（推定補正がそれ以上ならその終端まで）。実測後に4小節の範囲を切り出す。手前のカウントは旋律に含めず、遅延した曲末も保持する。
- 成功時の開始時刻は`musicalStart + measuredDelay + manualMs/1000`。推定遅延に実測を足さず、置き換える。失敗時はv7の推定開始フレームをそのまま使う。量子化前の時間基準を移すので、先頭休符の無条件削除ではない。
- 声の解析側は既存の低域通過フィルターで録音中シェーカーの高域を抑える。反響した波形の完全除去や加工音声の書出しを保証する機能ではない。
- 診断`capture.acousticTiming`に成否／理由、各カウントの予約・検出時刻・相関値、採用数・ばらつき、実測遅延、推定／適用補正、推定との差を16分単位に換算した`adjustmentTicks`、計測時間を追加。`unquantizedNotes`は丸め前の音区間。`timing.captureStartFrame/captureEndFrame`は収録全体、`startFrame/endFrame`は解析に使った4小節。
- 音声はWorker終了とともに破棄し、ファイル保存・外部送信・クリップボードへの波形出力をしない。記録は数値と音符のみ。既存の停止・マイクOFF・候補の2段階確定を維持。

## Windows 11の初回実機結果

timestamp `2026-09-27T01:24:33.513Z`。発案者は「欠落している音はあるがタイミングはOK」「前のめりでは歌っていない」と評価。120 BPM、48kHz、4096窓、短区間判定`energy-gated`、長音設定、ならし80ms、OS処理OFF、実測ON、追加補正0、頭詰め0、候補表示+1オクターブ。

**今回は実測補正の採用には至らず、従来の推定61msを使用。** `acousticTiming.status=unavailable`、理由`inconsistent-counts`、`source=estimated`、`inliers=3`、`adjustmentTicks=0`。検出したbeat0/4/5の差はそれぞれ約79.167/77.938/78.188ms（中央値78.188ms、範囲約1.23ms）、相関値0.522/0.600/0.389。beat2/6/7は未検出。3件の時刻差は近いが採用条件4件に届かず不採用であり、「大きくばらついた」とは解釈しない。候補中央値と推定値の差は約17.19ms（120 BPMの16分に対して約0.138tick）。自然な歌唱で合った所感は記録しつつ、実測補正が改善した証拠にはしない。

検出6音、開始tick `0,8,10,14,24,30`、長さ `7,2,2,9,4,28`、MIDI `54,51,52,54,50,47`。以前の7音と比べると、tick24〜28がC♯/D♯の2音ではなくD（50）の1音になっている。量子化前も3.0507〜3.4773秒のD1区間なので、16分丸めだけで消えた音ではない。別歌唱のため、原因が発声音程・検出・ならしのどこかは未確定。最後のBは約42.7msの有声不明区間を補完して1音を維持、冒頭半音補正履歴なし。289/375フレーム検出、不明12・0.256秒、全解析1485ms、クリック計測37.4ms。

Windows v7の直前ログは旧方式`window-start`、今回v8は`energy-gated`。実測補正の採否だけでなく方式・歌唱も異なるため、体感差の原因を断定しない。Pixelの次の結果を待ち、今回の受領ではコード・閾値・公開版を変更しない。

## Pixel 6aの実機結果：実測補正を採用しタイミング・音程OK

timestamp `2026-09-27T01:28:18.111Z`。発案者が「こちらもタイミングOK、音程もOK」と評価。120 BPM、48kHz、4096窓、`energy-gated`、長音設定、ならし80ms、OS処理OFF、実測ON、追加補正0、頭詰め0、候補表示+1オクターブ。v7の前のめり歌唱で合った結果とは別のv8実機結果として扱う。

- `acousticTiming.status=measured`、`source=acoustic`、6/6発採用。実測・適用遅延89.2396ms、推定43.6667msに対して45.5729ms大きい補正（16分の0.3646個ぶん）。両者を加算せず実測値で置き換えている。
- 6発の検出差の最大最小差は約0.167ms、相関値0.686〜0.890。今回のクリック間の一貫性を示す値であり、物理遅延の絶対精度が0.167msであるという意味ではない。計測62.7ms、全解析2650.6ms。
- 7音、開始tick `0,8,10,14,24,26,30`、長さ `7,2,2,9,2,2,29`、MIDI `54,51,52,54,49,51,47`。Windowsで1音のDになった区間はC♯→D♯の2音として保持。最後のBも29tickの1音、補完・冒頭半音補正なし。311/375フレーム検出、不明19・約0.405秒。候補と捕捉音符は一致、調号♯5。
- 45.6msは16分125msより短くても、最近傍丸めの境界を跨げば音符の開始tickが1つ変わり得る。今回のログは入出力経路の推定と実測の差を示すが、過去の全試行の遅れがこの差だけだったと断定しない。

このPixel試行を、実測補正を使用して発案者の聴感評価も得られた基準結果とする。Windowsのクリック検出不足・音の統合、Bluetooth、別BPM／別出力経路での実機精度は残課題。今回の受領ではコード・閾値・公開版を変更しない。
