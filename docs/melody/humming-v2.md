# ハナウタ試作v2 — 実機フィードバック対応

2026-09-27。発案者の「録音中のカウント、揺れる音高の平均化、最も近い半音と16分クオンタイズ、頭の16分休符への対処」の指示を受けた試作修正。本アプリ全体のQ1〜Q3承認とは区別する。

## 提供データと原因

| 端末・条件 | 音符数 | 先頭tick | pitched / 全frame | unknown | 解析時間 |
|---|---:|---:|---:|---:|---:|
| Pixel 6a、OS処理OFF | 25 | 1 | 244 / 375 | 39 | 2029.7ms |
| Windows 11、OS処理ON | 28 | 1 | 237 / 375 | 46 | 1189ms |
| Windows 11、OS処理OFF | 21 | 1 | 316 / 375 | 23 | 1410.8ms |

すべて120 BPM、48kHz、4小節。発案者はPixelの例で7音を歌った意図と報告。OS処理OFFでも細分化が残る。元処理は約21.3msごとの検出音高をすぐ半音化し、半音が変わるたびに別区間へ切るため、小さな揺れで多数の音符になる。さらに各微小区間を最低1tickに伸ばすため、区間数が多いほど後続の位置も押される。

提供JSONには生波形・浮動小数の音高列がない。丸め済みの音符から元の7音や遅延の真値を復元したとは扱わない。端末ID・groupIdは記録文書へ転載しない。

## 変更

- **音高のならし**：無音・不明区間を跨がず、中央値から離れた短い外れ値を除いて局所平均し、持続した音高変化だけで区間化。区間内の音高を時間で重み付けして平均し、最後に最も近い半音へ丸める。通常80ms／強め120ms／なしを比較できる。短い半音進行を潰さないよう変化確認時間は16分の半分以下にも制限。小さな半音境界越えは長めに継続確認し、冒頭の平均窓による片寄りも抑える。
- **16分単位**：区間の開始・終了を16分へ丸める。音高のならしは量子化前。無音を埋めず、休符を挟んだ同音は別音のまま。
- **録音中の拍**：準備8拍＋録音16拍を同じAudioContext時計で予約。高域6.5〜10.5kHzの短い非周期的なシェーカーを合成し、録音中のカウントがONなら解析前に3kHz低域通過フィルターをかける。フィルターは中心対称で時刻をずらさない。直近の録音欄に小節・拍を表示。停止時は予約音も取り消す。
- **遅延補正**：カウント音ONではAudioContextのbaseLatency・outputLatencyと入力trackのlatencyを初期推定に使用。音OFFでは入力latencyだけを使い、画面基準の歌声に出力機器の遅延を足さない。4小節の捕捉窓全体をずらし、末尾を切り捨てず16拍分を確保。追加補正−200〜400msを端末に保存。＋側で譜面上の取り込み位置が前へ移る。
- **候補の頭合わせ**：「頭の休符を詰める」で候補全体を先頭へ移動し、同じボタンで戻せる。音間の休符・音符長を維持し、採用前の元音列を変えない。自動で弱起を消す処理ではない。
- **測定**：prototypeをML-T01-v2へ更新。補正値とカウント時刻、ならし設定を記録。新しい録音開始時に日時と古い捕捉結果を更新し、deviceId/groupIdは報告から除く。

[Web Audio仕様](https://www.w3.org/TR/webaudio/)と[Media Capture仕様](https://www.w3.org/TR/mediacapture-streams/)にあるlatencyは推定値。歌い始めの反応時間、OS処理の揺れ、音響経路まで測定した校正値ではない。提供値の単純合計はPixel約44.7ms、Windows約61msだが、これだけで全症状が解消すると断定しない。

シェーカーは「物理的に録音されない音」ではない。帯域外に寄せ解析時に抑える方式で、スピーカーの歪みや環境による混入は実機再確認が必要。イヤホンまたはカウントOFFも選べる。音声を外部へ送信・保存しない。

## 検証

```powershell
$env:TZ='UTC'
node --test scripts/test-saezuri-humming.mjs scripts/test-saezuri-capture-timing.mjs
node scripts/test-saezuri-humming-browser.cjs
node scripts/test-saezuri-probe-browser.cjs
```

合成波形で7つの低い音＋ビブラートを7音へ整理し、16分の半音進行、実際のオクターブ変化、同音間の休符、意図的な弱起を保持する。44.1/48kHzでシェーカー単独が音符にならず、C3/A4/C7と混ぜても旋律を維持。Chromeで150ms遅れの7音をAudioWorklet→Workerへ通し、先頭tick0・7音・384000標本・24カウント・終了後のtrack解放を確認した。

レビューで見つかった「短い半音進行の消失」「カウント音OFF時の過剰補正」「端のオクターブ誤検出によるNaN」は回帰テストを追加して修正。ならし標準80msで実波形の半音進行を確認。強め120msは音高変化がよりまとまりやすい比較設定であり、実声で聞き比べる。

これは合成入力での回帰検証。修正版でのPixel 6a／Windows 11実声の改善度とiPhone Safariは未確認。提供ログを新算法で再解析した結果ではない。

## 未決の検討事項：カウントに食い込むシンコペーション

2026-09-27、発案者から記録用コメント：「カウントに食い込むシンコペーションをどうするか？」

録音開始の小節頭より前、準備カウント中に歌い始めるケースとして検討する。開始前から続く音の立ち上がりと長さをどう保持し、弱起や小節をまたぐ音として譜面・再生・4小節の範囲にどう扱うかは未決。意図的な先行発音と端末遅延を区別し、頭合わせで一律に小節頭へ寄せて解決したことにしない。

この追記は論点の記録であり、カウント区間の収録・保存範囲や実装方針の決定ではない。
